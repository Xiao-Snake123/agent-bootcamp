# 第 4 章 规划与分解

> 难度：★★★☆☆ ｜ 前置：第 1 章 ReAct ｜ 对应旧 K5

## 4.1 为什么纯 ReAct 不够
ReAct 是"走一步看一步"，遇到多步、有依赖、需前瞻的任务会迷路（例如"先调研 3 家再对比"——它容易做到第二步就忘了整体目标）。规划与分解让 Agent **先想清楚再动手**，把大目标拆成可执行的子任务结构。

## 4.2 两种范式
- **Plan-and-Execute**：先用一个"规划器"产出完整计划（任务列表/DAG），再逐个执行；执行中若偏离，触发重规划。
- **在线分解**：每完成一步，再决定下一步（仍是 ReAct 式，但带"子目标"显式表达）。
- 选型：任务可预见、依赖清晰 → Plan-and-Execute；环境高度不确定 → 在线分解。

## 4.3 任务结构：列表 / DAG / 目标树
```
Plan:
  1. 收集需求        (无依赖)
  2. 设计方案 A      (依赖 1)
  3. 设计方案 B      (依赖 1)
  4. 对比 A/B 并选型 (依赖 2,3)
  5. 产出报告        (依赖 4)
```
- **DAG**：表达依赖，支持并行执行无依赖节点。
- **目标树**：递归分解，叶子是原子动作。

## 4.4 最小规划器实现
```python
def plan(goal) -> list[str]:
    resp = llm.chat([
        {"role":"system","content":"把目标拆成有序、原子的步骤，每行一个。"},
        {"role":"user","content":goal},
    ])
    return [line for line in resp.splitlines() if line.strip()]

def execute_plan(plan):
    results = {}
    for step in plan:
        obs = run_step(step, context=results)   # 每步可调用工具/子Agent
        results[step] = obs
    return results
```
要点：规划与实际执行**分离**，便于插入"重规划"检查点。

## 4.5 重规划与回退
- 当某步 Observation 表明计划失效（工具报错、前提不成立），触发 `replan(goal, failed_step, reason)`。
- 回退：保留已完成步骤的成果，只重做受影响分支（DAG 增量重算），不要推倒重来。

## 4.6 分解粒度
- 太粗：一步做太多，模型易错且难纠错。
- 太细：步骤爆炸，上下文与管理开销大，且每步都要 LLM 调用 → 成本/延迟上升。
- 经验：叶子步骤应"一次工具调用或一次明确推理能完成"。

## 4.7 论文与延伸
- Tree of Thoughts（arXiv:2305.10601）：把推理建成树，搜索多条思路再选优——适用于需要探索的任务。
- Plan-and-Solve Prompting：先计划再执行，缓解 ReAct 的短视。
- 延伸：第 9 章把计划表达成可恢复的图（checkpoint）。

## 4.8 面试考点
1. **规划与实际执行不一致怎么处理？** 答：设重规划检查点，基于失败观测局部重做，保留已完成成果。
2. **分解过细/过粗的代价？** 答：过粗易错难纠；过细上下文与调用成本爆炸。
3. **Plan-and-Execute 与 ReAct 怎么选型？** 答：依赖清晰可预见用前者；环境不确定用后者（或二者结合：先粗计划再逐步执行）。

## 4.9 常见坑
- **规划阶段不验证可行性** → 计划漂亮但第一步就调不通。
- **忽视依赖顺序** → 并行执行有依赖的步骤导致数据缺失。
- **计划写死、不允许重规划** → 环境一变就崩。
