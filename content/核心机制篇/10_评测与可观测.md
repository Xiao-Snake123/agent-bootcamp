# 第 10 章 评测与可观测

> 难度：★★★★☆ ｜ 前置：第 1–9 章 ｜ 对应旧 K12

## 10.1 为什么评测是 Agent 的"难中之难"
LLM 应用还能用"输出对比参考答案"评测；Agent 多步、有工具、有随机性，**结果对不一定过程对**（瞎调工具碰巧答对），过程对也不一定结果对（工具临时故障）。必须同时评"过程"和"结果"。

## 10.2 过程级 vs 结果级
- **结果级**：最终答案是否正确/达标（易自动，但掩盖问题）。
- **过程级**：是否调用了正确工具、步数是否合理、有无越权/无效调用、是否触发反思。
- 二者都要：只看过结果会放过"碰巧对"的脆弱 Agent。

## 10.3 轨迹回放（Trajectory Replay）
把每次运行的 (thought/action/observation) 全量记录，离线回放分析：
- 哪些步骤是冗余/无效？
- 哪次工具调用是失败根因？
- 同一任务多次运行的一致性（稳定性）如何？
这是定位 Agent 行为的核心手段（呼应 `agent_core/eval.py` 的 Trajectory）。

## 10.4 LLM-as-Judge
用强模型当裁判给 Agent 输出打分（相关性/忠实度/安全性）。注意偏差：
- 位置偏差（偏好靠前的）、冗长偏差（偏好更长）、自我偏好（偏好同为某模型生成）。
- 缓解：多裁判投票、给评分 rubric、与确定性指标交叉验证。

## 10.5 护栏（Guardrails）
在三个点拦截：
- **输入护栏**：过滤注入/敏感请求（第 11 章）。
- **过程护栏**：限制工具调用次数/权限/金额（呼应第 2、12 章）。
- **输出护栏**：检测泄露/有害/格式错误再修正或拒绝。

## 10.6 成本与延迟度量
- 每次运行的 token 数、工具调用次数、总延迟、成功率。
- 建立"成本-质量"曲线：同一任务在不同模型/策略下的权衡，指导选型。

## 10.7 评测基准
- AgentBench（arXiv:2308.03688）：多环境 Agent 能力基准。
- 自建离线集：针对你的任务收集"输入-期望轨迹/答案"对，回归测试防退化。

## 10.8 面试考点
1. **结果对但过程错的 Agent 算好吗？** 答：不算。过程错意味着脆弱、不可复现，换次运行可能失败；必须过程+结果双评。
2. **LLM-as-Judge 的偏差如何缓解？** 答：多裁判投票、明确 rubric、与确定性指标交叉验证、警惕位置/冗长/自我偏差。
3. **如何防 Agent 评测退化？** 答：建离线评估集做回归测试，每次改 prompt/逻辑都跑全集对比指标。

## 10.9 常见坑
- **只看最终答案** → 放过碰巧答对，上线即崩。
- **没有离线评估集就上线** → 无法量化改动影响，靠手测盲改。
- **护栏只做输出层** → 过程里已越权/烧钱，输出层拦不住。

## 10.10 配套可运行 demo
`demos/demo_10_eval.py`（模块：`agent_core.eval.TrajectoryEvaluator` / `EvalCase`）：

```bash
python demos/demo_10_eval.py --offline
```
复用 `Agent.run()` 产出的 `Trajectory`，把评测拆成可解释的六项检查：
是否给出答案、关键词命中率、是否正常终止（`stop_reason`）、是否调用禁用工具、
失败工具调用数、步数效率；加权得到分数并形成套件报告。

这正是 10.2「过程 + 结果双评」的落地：只判最终答案会放过"瞎调工具碰巧答对"。
另见 `tests/test_agent_core.py` 的离线契约测试与 `demos/run_all.py` 一键回归。
