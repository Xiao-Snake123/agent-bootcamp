# 第 6 章 多 Agent 协作

> 难度：★★★★☆ ｜ 前置：第 1–5 章 ｜ 对应旧 K7

## 6.1 为什么要多 Agent
单 Agent 加再多工具，仍是"一个人在战斗"：上下文混杂、角色冲突、长任务易失焦。**多 Agent** 把不同职责分给专门角色（规划者/执行者/ critic/检索者），通过消息协作，换取专长隔离、上下文隔离与并行。

## 6.2 核心组件
- **角色（Role）**：每个 Agent 有独立 system + 工具集 + 记忆。
- **消息总线 / 共享黑板**：Agent 间传递消息的通道（共享状态或消息队列）。
- **Orchestrator**：协调者，负责派活、汇总、决定终止（或去中心化辩论）。
- **通信协议**：消息需结构化（sender/recipient/intent/payload），否则解析脆弱。

## 6.3 编排模式
- **Orchestrator-Worker**：协调者分解任务、派给 worker、回收结果（最常用）。
- **辩论/共识**：多个 Agent 对同一问题各自论证，再用一个聚合者裁决（提升质量，代价是调用量×N）。
- **流水线**：Agent A 输出 → Agent B 输入，串行专精（如 检索→摘要→校验）。

## 6.4 最小实现（共享消息总线）
```python
class MultiAgent:
    def __init__(self): self.agents = {"planner":..., "coder":..., "critic":...}
    def run(self, goal):
        msg = {"from":"user","to":"planner","payload":goal}
        board = [msg]
        while not done(board):
            m = pop_next(board)
            resp = self.agents[m["to"]].chat(board)        # 各 Agent 看得到黑板
            board.append({"from":m["to"],"to":resp.next,"payload":resp.text})
        return last_answer(board)
```
关键：每个 Agent 的 `chat` 只暴露**相关**黑板内容，避免上下文爆炸（上下文工程，第 3 章）。

## 6.5 资源共享与死锁
- 共享工具/记忆要处理并发（第 2 章写操作串行）。
- 死锁：A 等 B、B 等 A。需超时 + Orchestrator 兜底仲裁。
- 信息丢失：消息未带足够上下文导致下游误解 → 消息协议要含必要背景。

## 6.6 与单 Agent + 工具的边界
不是"更多 Agent 更好"。经验：
- 任务能靠单 Agent + 好工具解决 → 不要拆多 Agent（延迟/成本叠加）。
- 需要**强上下文隔离**（如一个 Agent 看机密数据、另一个不能看）或**真正并行专长**时才上多 Agent。

## 6.7 工业实现
- **AutoGen**（arXiv:2308.08155）：对话式多 Agent，支持 human-in-the-loop。
- **CrewAI**：角色+流程的叙事式编排。
- **Generative Agents**（arXiv:2304.03442）：斯坦福"小镇"，记忆+规划+反思的社会化 Agent。

## 6.8 面试考点
1. **何时该用多 Agent 而非单 Agent+工具？** 答：需强上下文隔离、真正并行专长、或角色职责清晰分离时；否则单 Agent 更省。
2. **多 Agent 通信瓶颈？** 答：消息协议脆弱、上下文膨胀、协调者成单点；需结构化消息+选择性可见+超时仲裁。
3. **如何避免多 Agent 信息丢失/重复？** 答：消息带必要背景、共享黑板去重、Orchestrator 做汇总。

## 6.9 常见坑
- **过度编排** → 每层 Agent 都调 LLM，延迟与成本叠加数倍。
- **消息无 schema** → 自由文本传递，下游解析失败率高。
- **协调者无终止条件** → Agent 互相委派，永不结束。
