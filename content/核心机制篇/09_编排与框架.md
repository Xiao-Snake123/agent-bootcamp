# 第 9 章 编排与框架

> 难度：★★★★☆ ｜ 前置：第 1–8 章 ｜ 对应旧 K11

## 9.1 编排要解决的问题
前面每章都是一个"能力"，编排（Orchestration）是把它们串成**可恢复、可观测、可暂停**的流水线：从"一个目标"到"最终结果"，中间可能经历规划→多步工具→反思→多 Agent 协作，任何一步都可能失败或需要人工介入。

## 9.2 声明式图 vs 命令式
- **命令式**：用 Python `while/if` 手写循环（第 1 章 demo）——灵活但难恢复、难观测。
- **声明式图**：把流程定义为 Node/Edge 的有向图，运行时按图推进，状态外置——天然支持 checkpoint、回放、human-in-the-loop。
```python
# 伪代码（LangGraph 风格）
graph = StateGraph(AgentState)
graph.add_node("plan", planner)
graph.add_node("act", actor)
graph.add_node("reflect", reflector)
graph.add_edge("plan", "act")
graph.add_conditional_edges("act", route_on_obs)  # 成功→结束，失败→reflect，reflect→act
compiled = graph.compile(checkpointer=...)
```

## 9.3 核心概念
- **State**：图的累加状态（消息、记忆、中间结果），是恢复的最小完备信息。
- **Node**：一个处理单元（调用 LLM/工具/子图）。
- **Edge / Conditional Edge**：流转规则（含人工审批边：暂停等输入）。
- **Checkpoint**：把 State 落盘，支持从中断点恢复（断电/人工介入后继续）。

## 9.4 Human-in-the-loop（暂停恢复）
关键场景：高风险动作（发邮件/支付/删数据）前暂停，把当前 State 存 checkpoint，等人工确认 `resume(state, approval)` 继续。这是工具系统（第 2 章）与编排的交汇点。

## 9.5 幂等：恢复命门
恢复时某个 Node 可能**被重跑**，若它副作用不幂等（如重复扣款），恢复反而制造事故。原则：写操作 Node 必须幂等（带去重键/事务），或只在"已确认"边执行。

## 9.6 框架源码级对比
- **LangGraph**：图 + checkpoint + 状态通道，最贴近"可恢复编排"，适合复杂流程。
- **AutoGen**：对话驱动的多 Agent 编排，human-in-the-loop 内建。
- **CrewAI**：角色+任务的高层叙事，上手快但底层可控性弱。
- 自研 vs 框架：流程简单用命令式即可；需恢复/观测/暂停用框架，避免重写状态机。

## 9.7 与第 4 章计划的关系
计划（DAG/目标树）是"逻辑结构"，编排图是"运行时结构"。可把计划直接编译成编排图的初始拓扑，执行中再动态加边（重规划）。

## 9.8 面试考点
1. **checkpoint 应存哪些最小完备状态？** 答：当前 State（消息/记忆/变量）+ 执行指针（在哪个 Node/边）+ 未完成子任务；足以无副作用恢复。
2. **幂等为什么是恢复命门？** 答：恢复会重跑 Node，非幂等副作用（扣款/发信）会重复发生。
3. **自研 vs 用框架怎么选？** 答：简单线性用命令式；需 checkpoint/回放/HITL 用框架，别重造状态机。

## 9.9 常见坑
- **编排逻辑写死在业务代码** → 无法暂停/恢复/观测。
- **恢复点不落盘** → 进程崩了只能从头跑，长任务灾难。
- **Node 副作用不幂等** → 恢复即事故。
