# 项目教学模块（Lab Zone）设计文档

> 配套：《01_整体设计方案.md》《02_文字教学模块设计文档.md》。
> 本模块负责"怎么造 / 跑起来"，与理论模块一一咬合；所有 Lab 共用 `agent_core` 骨架。

---

## 1. 模块定位与目标

- **目标**：把理论变成可运行能力；每知识点对应一个能跑、能验证、能回扣理论的项目。
- **能力映射**：L1–L12 一对一映射 K1–K12；做到 L12 时 `agent_core` 已长成具备零件库的运行时，供大项目直接复用。
- **职责边界**：交付可运行代码 + README + 验收 + reflection；不替学习者写完整业务，只给骨架与关键实现要点。

---

## 2. 共用骨架 `agent_core` 设计（关键）

> 这是双区"主线贯穿"的引擎。所有 Lab 都是往这个骨架插模块。P0 必须先把骨架跑通。

### 2.1 设计原则
- **本地优先**：默认本地模型/本地向量库可跑，零云依赖也能完成基础 Lab。
- **接口稳定**：骨架抽象（LLMClient / Tool / Memory / Agent）不随框架变；框架仅作可选适配层。
- **模块可插拔**：每个能力 = 一个注册到 `Registry` 的模块，组合即系统。
- **工具抽象统一**：K3 的本地工具、K9 的 MCP 远端工具、K10 的 Skill 绑定工具，**都收敛到同一 `ToolRegistry`**——这是"工具接入主线"在代码层的落点。

### 2.2 核心抽象

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass, field

@dataclass
class Action:        # 模型决定要做的动作
    name: str
    args: dict

@dataclass
class Observation:   # 动作执行后的观察
    content: str
    ok: bool = True

class LLMClient(ABC):
    @abstractmethod
    def complete(self, messages, **kw) -> str: ...

class Tool(ABC):
    name: str; schema: dict
    @abstractmethod
    def run(self, **args) -> Observation: ...

class Memory(ABC):
    @abstractmethod
    def add(self, item): ...
    @abstractmethod
    def get(self, query, k=4) -> list: ...

@dataclass
class Trajectory:
    steps: list = field(default_factory=list)

class Agent:
    def __init__(self, llm, tools=None, memory=None): ...
    def run(self, goal: str, max_steps=10) -> tuple[str, Trajectory]: ...
```

### 2.3 最小骨架（P0 交付，可跑通 mock 工具循环）
- `agent_core/llm.py`：LLMClient 封装（OpenAI 格式 + Ollama 兜底）。
- `agent_core/tools.py`：Tool 基类 + 注册表 + 校验/重试分发器（K3/L3 已用）。
- `agent_core/memory.py`：Memory 基类（Buffer 短期 + 可选 Vector 长期）。
- `agent_core/agent.py`：Agent.run 最小 Loop + Trajectory 记录。
- `agent_core/registry.py`：模块注册机制（后续 Lab 往里挂 Planning/Reflector/...）。

## 3. 实现路径

- **每个 Lab = 独立可运行脚本 + tests + README + reflection**。
- **不引入重框架直到 K11**：L1–L10 用纯 Python + `agent_core`；L11 起可引入图编排（自写或对照 LangGraph）。
- **验收双轨**：`pytest` 自动化验收测试 + 人工 `python run.py` 跑通看演示。
- **密钥与成本**：密钥走 `.env`；`LLMClient` 内置 token 计数与成本上限，超限抛错。
- **提交节奏**：每完成一个 Lab 打一个 commit，消息形如 `L03: 工具调用机器人（K3）`。

## 4. 项目总表（L1–L12）

> 列法：对应K / 主题 / 能力目标 / 任务拆解 / 验收标准 / 关键实现要点 / 交付物。

### L1 最小 Agent Loop 模拟器（K1）
- **目标**：实现"思考→工具→观察→再思考"循环并正确终止。
- **任务**：定义 Agent 类；实现 `decide/execute`；用 mock 工具（如计算器）跑通；打印 Trajectory。
- **验收**：给定目标能自主循环 ≤N 步并终止，轨迹可读（含 Thought/Action/Observation）。
- **要点**：先 mock 工具跑通 Loop，再接真 LLM；终止条件（Final Answer / 步数上限）。
- **交付**：`loop.py` + README + 轨迹示例。

### L2 提示工程练习台（K2）
- **目标**：设计 System Prompt，稳定产出符合 schema 的 JSON。
- **任务**：写 prompt 模板；调用 LLM 输出结构化 JSON；用 pydantic/json-schema 校验。
- **验收**：输入需求稳定产出合规 JSON（含非法输入降级处理）。
- **要点**：schema 校验 + 失败重试解析；temperature 调低保稳定。
- **交付**：`prompt_lab.py` + 校验脚本 + README。

### L3 工具调用机器人（K3）✅ 已完成
- **目标**：注册天气/计算器/搜索工具、参数校验、失败重试；理解 FC 协议与 `tool_call_id` 配对。
- **任务**：`tools_to_openai_schema` 转 schema；`FunctionCallingAgent.run` 消费 `tool_calls` → 校验 → dispatch（失败重试）→ 带 `tool_call_id` 回灌；离线 `MockFunctionCaller`。
- **验收**：单工具 / 并行 / 搜索三轨迹跑通；未知工具拒绝；pytest 7 passed（含 `tool_call_id` 配对）。
- **要点**：Tool 基类 + 注册表；并行调用用 `tool_call_id` 配对；mock 的 `thought` 仅为离线演示（真实 API 无此字段）。
- **交付**：`tools_fc.py` / `fc.py` / `mock_fc.py` / `test_fc.py` / README / reflection。

### L4 有记忆对话助手（K4）
- **目标**：短期+长期记忆，跨轮召回且不爆窗。
- **任务**：Buffer 短期 + Vector 长期（Chroma/FAISS）；召回注入上下文；摘要压缩。
- **验收**：隔若干轮仍能引用早期信息；长对话不溢出窗口。
- **要点**：Memory.add/get；长文本摘要淘汰策略。
- **交付**：`memory/` 模块 + README + 跨轮演示。

### L5 ReAct 推理机器人（K5）
- **目标**：Reason+Act 交替，靠工具逐步推理多跳问题。
- **任务**：ReAct prompt 模板；解析 Thought/Action/Observation；步数上限。
- **验收**：复杂多跳问题能靠工具逐步得出答案。
- **要点**：结构化解析（正则/分段）；Observation 必须回灌下一轮。
- **交付**：`reasoning/react.py` + README + 多跳示例。

### L6 任务分解执行器（K5/K6）
- **目标**：Plan-and-Execute，依依赖有序执行子任务；接反思自评。
- **任务**：Planner 产出任务树；Scheduler 按依赖执行；结果回写；Critic 有限次修正。
- **验收**：输入"做一次市场调研"输出有序执行结果，且能自检修正。
- **要点**：任务树建模依赖；执行与计划解耦；critic 反馈须具体。
- **交付**：`planning/` + `reflection/` 模块 + README。

### L7 多智能体协作台（K7）
- **目标**：角色消息传递与协作产出。
- **任务**：Researcher/Writer/Critic 三角色；message bus；编排者路由与终止。
- **验收**：三方协作产出一份带评审意见的文稿。
- **要点**：角色职责不重叠；明确终止；上下文隔离避免爆炸。
- **交付**：`multiagent/` 模块（角色+总线）+ README。

### L8 本地文档问答助手（K8）
- **目标**：RAG 全流程，准确回答并标注出处。
- **任务**：切片→嵌入→建库→检索→重排→注入→生成；出处标注。
- **验收**：基于给定 PDF/文档准确回答，标注引用片段。
- **要点**：chunk 大小调参；重排降噪；query rewrite；citation 不可省。
- **交付**：`rag/` 模块 + README + 问答示例。

### L9 MCP 接入台（K9）
- **目标**：把 `tutorial/code/mcp_demo` 的 MCP server 接入为 `agent_core` 的工具源。
- **任务**：写 MCP client bridge → `initialize` → `tools/list` → 包装成本地 `Tool` → `registry.register`；调用经 `tools/call` 转发。
- **验收**：Agent 不改动主循环即可调用远端工具；换 server 不影响 Agent 代码。
- **要点**：transport 选择（stdio / SSE）；远端 schema 与本地校验对齐；auth/权限边界。
- **交付**：`mcp_bridge/` 模块 + README + 远端调用演示。

### L10 Skill 能力模块（K10）
- **目标**：定义 Skill、实现按需发现与加载。
- **任务**：用 `tutorial/code/skill_demo` 的真实 Skill，做"路由→取提示+工具+流程→注入 Agent"的最小演示；区分 Skill 与 MCP。
- **验收**：Agent 遇到匹配任务时按需加载 Skill，注入后行为变化；不加载时不占用上下文。
- **要点**：Skill 描述（名称/触发条件/绑定工具/步骤）清晰；不与基础 system 冲突；版本化。
- **交付**：`skill/` 模块 + README + 加载演示。

### L11 工作流编排器（K11）
- **目标**：图/状态机串联 L3–L10 模块，支持中断恢复。
- **任务**：用图声明流程；checkpoint 持久化；human-in-the-loop 节点。
- **验收**：可视化跑通多步流程并能从断点续跑。
- **要点**：节点=已注册模块；edge=流转；checkpoint 保证幂等与可恢复。
- **交付**：`orchestration/` 模块 + README + 流程图。

### L12 评估与日志面板（K12）
- **目标**：轨迹追踪 + 自动评分（含 LLM-as-judge）+ 成本统计。
- **任务**：记录每步输入输出；多维评分；成本/延迟统计；产出报告。
- **验收**：一次运行产出可读报告（步骤/耗时/花费/评分）。
- **要点**：复用 Trajectory；评分维度可配置；护栏可插拔。
- **交付**：`observability/` 模块 + README + 报告样例。

## 5. 成果交付规范

每个 Lab 交付四件套：
1. **代码**：可运行，挂入/扩展 `agent_core`。
2. **README**：目标、步骤、验收、如何运行、关键决策。
3. **Demo**：轨迹/截图/示例输入输出。
4. **Reflection（回扣理论）**：回答三问——① 本 Lab 验证了理论的哪一点？② 实现中踩了什么坑（对应理论"常见陷阱"）？③ 若重做会改什么？

**评分维度（用于阶段验收）**
| 维度 | 权重 | 标准 |
|------|------|------|
| 跑通 | 40% | 满足验收标准，pytest 通过 |
| 代码质量 | 20% | 接口清晰、命名规范、有注释 |
| README | 20% | 目标/步骤/验收/运行说明完整 |
| Reflection | 20% | 三问回答到位，能反指理论点 |

## 6. 大项目（Capstone）详细设计

### 6.1 主题（三选一，按学员背景定）
- **A. 深度研究助理（默认样例）**：输入开放问题→自主规划→多源检索→多方辩论交叉验证→起草→自审→带引用长文；全程可观测、成本可控。
- **B. 个人自动化运营台**：连接邮件/日历/文件/API，按自然语言完成跨系统多步任务（**MCP 接外部系统 + Skill 封装常用流程 + 评估护栏**）。
- **C. 代码工程 Agent**：需求→拆任务→写码→跑测试→自审修复→提 PR。

### 6.2 架构（以 A 为例）
```
用户问题 → Orchestrator(主控, K11+K6)
   ├ Researcher(K5/K7) 规划子任务、检索
   ├ Critic(K6/K7)    辩论/挑错
   ├ Writer(K7)       起草报告
   ├ Retriever(K8)    RAG 知识接地
   ├ MCP Bridge(K9)   接外部工具/数据源
   ├ Skill Loader(K10) 按需加载领域能力
   ├ Reflector(K6)    终稿自审
   └ Eval&Observability(K12) 轨迹/评分/成本/护栏
```

### 6.3 模块登记（复用 L1–L12 零件库）
把各 Lab 成果注册为可插拔模块：Tool / Memory / Planner / Reflector / Retriever / MCPBridge / SkillLoader / Orchestrator / Evaluator。

### 6.4 里程碑 M0–M6
- **M0** 骨架复用：直接以 `agent_core` 为底座。
- **M1** 模块登记：注册九大+模块（含 MCP/Skill）。
- **M2** 编排层：图串联成流水线。
- **M3** 知识接地：接入 RAG/MCP。
- **M4** 反思闭环：Writer 产出后强制过 Critic+Reflector。
- **M5** 工程化收口：轨迹/评分/成本/护栏。
- **M6** 演示与复盘：≥3 个真实问题端到端跑通 + 设计决策说明书。

### 6.5 验收
- [ ] 端到端完成 ≥3 个真实复杂任务，无需人工逐步干预；
- [ ] 每个能力模块可在报告中溯源到对应知识点（K3/K9/K10 等）；
- [ ] 具备可观测性：任一次运行可回放完整轨迹、定位失败环节。

### 6.6 交付物
系统代码 + **设计决策说明书**（每个模块→知识点溯源 + 选型理由）+ 演示录像/脚本 + 代码走查记录。

## 7. 工程规范

- **仓库**：`agent_core/` `labs/` `capstone/` `docs/`，根置 `glossary.md` `.env.example`。
- **git**：每 Lab 一 commit；每阶段一 tag（如 `phase-3`）。
- **测试**：每 Lab 至少 1 个 pytest 验收测试；CI 跑 `pytest labs/`。
- **环境**：`requirements.txt` 分层（base / rag / orchestration / mcp）；`.env.example` 列全部密钥名。
- **成本**：`LLMClient` 统一计数 token，设 `MAX_COST` 上限，超限抛 `CostLimitError`。
- **风格**：black + ruff；模块接口与类型注解保持一致。
