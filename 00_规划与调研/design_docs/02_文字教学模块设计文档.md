# 文字教学模块（Theory Zone）设计文档

> 配套：《01_整体设计方案.md》《03_项目教学模块设计文档.md》。
> 本模块负责"为什么 / 是什么 / 怎么想"，与项目模块一一咬合。

---

## 1. 模块定位

- **目标**：让学习者建立 Agent 的统一心智模型（感知—思考—行动—观察—记忆的闭环），掌握原理而非只会调 API。
- **职责边界**：讲清概念、机制、范式、选型与陷阱；不替项目模块写完整代码，只给原理级伪代码/最小示例。
- **衔接**：每章末尾"动手引子"指向对应 Lab（前向钩子）；Lab 末尾"回扣理论"反向指回本章（反向钩子）。

---

## 2. 内容结构标准（章节模板）

每一章**固定 7 节**，保证教学一致性。逐节写作要素：

| 节 | 名称 | 必含要素 | 写作规则 |
|----|------|----------|----------|
| 1 | 学习目标 | 3–5 条可验证目标（动词：能解释/能画出/能对比/能设计） | 不用"了解"，用可观测动词 |
| 2 | 核心概念 | 定义 + 边界 + 与其他概念关系 | 配"概念卡"（一词一卡，定义≤2 行） |
| 3 | 工作原理 | 机制拆解 + 流程图/伪代码 + 关键协议/公式 | 图用 mermaid；伪代码 Python 风格 |
| 4 | 主流方案 | 代表框架/论文/范式 + 选型对比表 | 标明适用场景与取舍，不做广告 |
| 5 | 常见陷阱 | 新手易错点 + 反例 | 每条配"为什么错" |
| 6 | 自检题 | 3–5 题，附答案要点 | 含 1 道开放题（设计/对比） |
| 7 | 动手引子 | 明确 Lab 编号 + 前置条件 + 要验证的理论点 | 前向钩子，落到具体动作 |

**通用写作规则**
- 术语来自 `glossary.md`，禁止同词多义。
- 图优先 mermaid（流程图/时序图/类图）；伪代码 Python 风格、可运行。
- 语气：有观点、二阶口吻；示例具体（给真实片段而非"等等"）。
- 篇幅：核心章 1500–3000 字 + 至少 1 图 + 至少 1 段伪代码。
- **前沿要求（铁律）**：必须写 2025–2026 实务（如 prompt caching、native structured outputs、流式 tool call、reasoning 模型特性、MCP/A2A 协议、LLM-as-judge），不停留在教科书基础定义；每句必须有用，不堆砌名词。

## 3. 章节规划（K1–K12）

> 列法：阶段 / 前置 / 学习目标 / 核心概念 / 原理要点 / 关键图·伪代码 / 常见陷阱 / 自检题示例 / 动手引子。

### K1 Agent 概念与边界（执行阶段 P1，无前置）
- **目标**：能区分 Agent / Chatbot / 工作流 / RPA；能口述 Agent Loop 四阶段；能判断"何时该/不该用 Agent"。
- **概念**：Agent、环境、感知、行动、观察、自主性、Agent Loop。
- **原理**：感知→思考→行动→观察 闭环；与"一次性 LLM 调用"的本质区别（有无自主循环与工具副作用）。
- **图**：Agent Loop 流程图（感知→思考→行动→观察→回到思考，含终止判断）。
- **陷阱**：把"调一次 API"当 Agent；忽视终止条件导致死循环；把简单 if-else 流程硬说成 Agent。
- **自检**：Agent 与 Chatbot 的根本区别？什么任务不适合用 Agent？
- **引子→L1**：用 mock 工具实现最小循环，验证你能跑通"思考→行动→观察"闭环。

### K2 LLM 基础与提示工程（执行阶段 P1，前置 K1）
- **目标**：理解 token/上下文窗口；能写结构化输出 prompt；能设计 System Prompt 约束行为；理解 JSON mode 与 function mode 的区别。
- **概念**：token、上下文窗口、temperature/top-p、system/user/assistant、few-shot、JSON schema、function/JSON mode。
- **原理**：采样参数如何改变输出；结构化输出靠 schema 约束与校验；"提示"是 Agent 可控性的第一道闸门。
- **图**：prompt 组成图；temperature 高低对照表。
- **陷阱**：上下文溢出不分段；靠"请输出 JSON"而非 schema 校验导致格式不稳。
- **自检**：temperature 高低的适用场景？如何稳定拿到可解析 JSON？
- **引子→L2**：写提示词模板，让 LLM 稳定产出符合 schema 的 JSON。

### K3 工具调用 Function Calling（执行阶段 P2，前置 K2）
- **目标**：能定义工具 schema；能处理参数校验与失败重试；理解 FC 协议与"Agent 动手"的能力根基；能说清 **FC 与 MCP/Skill 的分层关系**。
- **概念**：
  - **Function Calling（FC）** = LLM 的原生能力——模型不再只吐文本，而是返回结构化的 `tool_calls`（要调哪个函数 + 参数 JSON），由你的代码执行。这是 Agent 从"会说"到"会做"的分水岭。
  - **Tool Use**（Anthropic 叫法，与 FC 同义，协议已趋统一）。
  - tool_call / **tool_call_id**（调用的唯一标识，回灌时配对）/ observation / schema / parallel vs sequential / **tool_choice** / prompt caching。
- **原理**：模型输出 tool_call → 代码按 schema 校验 → 外部执行 → 回灌 observation。OpenAI/Anthropic 格式已趋统一。**FC 是"模型调工具的协议层"；MCP（K9）是"工具从哪来的传输层"；Skill（K10）是"能力封装层"——三者分层，K3 只深讲 FC 本身。**
- **图**：tool_calls 往返时序图（一轮多工具并行 + 每个 tool 消息带 `tool_call_id` 配对）。
- **伪代码**：`dispatch(tool_calls)` → schema 校验 → 执行 → 收集 observation（每条带 `tool_call_id`）。
- **2025–2026 实务（必写）**：native structured outputs / strict JSON schema mode；**prompt caching** 缓存工具定义降本；`tool_choice` 强制/指定（required / 指定函数名）；**流式 partial tool call**（SSE 下 arguments 分片到达，按 id 拼接）；reasoning 模型（o1/o3/GPT-5）的工具调用特性（是否支持并行/流式查模型卡）；工具结果过大 → 截断/摘要防爆窗烧钱。
- **陷阱**：description 含糊；schema 不严；并行强顺序依赖；不校验参数；tool 结果缺 `tool_call_id`；工具结果过大；`tool_choice` 误设；幻觉工具名；把 thought 当协议字段；过度拆分工具。
- **自检**：FC 与"让模型输出 JSON"本质区别？**FC 与 MCP 的关系（协议层 vs 传输层）？** 何时该串行？
- **引子→L3**：注册天气/计算器/搜索工具，跑通单工具、并行与未知工具拒绝，确认 `tool_call_id` 配对。

### K4 上下文与记忆（执行阶段 P2，前置 K2）
- **目标**：区分短期/长期记忆；用向量库做长期记忆；做摘要压缩控制窗口。
- **概念**：short-term、long-term、vector store、embedding、summary compression、buffer/window、淘汰。
- **原理**：记忆写入/检索/淘汰；向量化检索流程（query→embed→检索→注入）。
- **图**：记忆模块图（写入/检索/压缩三路）。
- **陷阱**：把所有历史硬塞上下文→爆窗口；检索不相关却注入；长期记忆永不淘汰。
- **自检**：何时用短期 vs 长期？如何在不丢信息下压缩？
- **引子→L4**：给对话助手加短期+长期记忆，跨多轮召回早期信息。

### K5 推理与规划（执行阶段 P3，前置 K3）
- **目标**：能实现 ReAct；对比 CoT / ReAct / ToT；能 Plan-and-Execute 做任务分解。
- **概念**：CoT、ReAct（Thought/Action/Observation）、ToT、Plan-and-Execute、dependency graph。
- **原理**：Reason 与 Act 交替；先整体规划再逐步执行；子任务依赖决定执行顺序。
- **图**：ReAct 循环图 + 任务树（根目标→子任务→叶子动作）。
- **陷阱**：Action 格式错导致解析失败；无步数上限→死循环；Observation 不回灌；计划过细/过粗；不显式建模依赖。
- **自检**：ReAct 相比纯 CoT 多出了什么？Plan-and-Execute 相比直接 ReAct 的优势？
- **引子→L5**：用 ReAct 模板靠工具逐步推理多跳问题；L6 做规划分解。

### K6 反思与自评（执行阶段 P3，前置 K5）
- **目标**：能实现 Critic 循环；错误回溯与有限次重试；能接 LLM-as-judge。
- **概念**：reflection、self-critique、critic、retry、error trace、LLM-as-judge。
- **原理**：产出→评审→修正；评审须具体可操作；judge 模型给多维评分。
- **图**：critic 循环图（产出→评审→修订）。
- **陷阱**：批评空泛无修正抓手；无限重试烧成本；不区分"可修"与"需重做"。
- **自检**：有效的 critic 反馈应具备什么特征？何时该放弃重试？
- **引子→L6**：让机器人对含错代码自检并产出修正版（L7 落 Skill 前先看反思）。

### K7 多智能体（执行阶段 P4，前置 K6）
- **目标**：设计角色分工；实现消息传递；落地协作/辩论/评审范式。
- **概念**：role、message bus、orchestrator、debate、review、handoff。
- **原理**：多角色消息流；编排者负责路由与终止；与 K5 规划、K6 反思组合成复杂系统。
- **图**：三种拓扑——流水线（顺序）、辩论（环形）、评审（生成+ critic）。
- **陷阱**：角色冗余职责重叠；无明确终止条件；各角色上下文互灌→爆炸。
- **自检**：何时用多 Agent 而非单 Agent + 子程序？评审拓扑如何避免僵局？
- **引子→L7**：搭研究员+写手+评审三角色，协作产出带评审意见的文稿。

### K8 检索增强生成 RAG（执行阶段 P5，前置 K4）
- **目标**：搭 RAG 全流程；掌握切片/嵌入/检索/重排与出处标注。
- **概念**：chunk、embedding、retrieval、rerank、query rewrite、citation。
- **原理**：离线建库（切片→嵌入→存向量）+ 在线检索注入（query→检索→重排→拼接→生成）。
- **图**：RAG pipeline（离线/在线两阶段）。
- **陷阱**：chunk 过大/过小；无重排导致噪声；不标注来源→幻觉难查；query 不重写。
- **自检**：chunk 大小如何影响召回？重排解决什么问题？
- **引子→L8**：基于本地 PDF/文档做问答，准确回答并标注出处。

### K9 工具与外部集成 MCP（执行阶段 P5，前置 K3）
- **目标**：能说清 MCP 是什么（协议三原语 tools/resources/prompts）；能照 `tutorial/code/mcp_demo` 做一个 MCP server 并暴露工具；能把任意 MCP server 接入 Agent（作为 ToolRegistry 的工具源）。
- **概念**：Model Context Protocol、MCP server / client、`initialize` / `tools/list` / `tools/call`、resources、prompts、transport（stdio / SSE / streamable HTTP）。
- **原理**：Agent 侧用 MCP client 连 server → `initialize` → `tools/list` 拿到远端工具 schema → 把远端工具"翻译"成本地 `Tool` 注册进 `ToolRegistry` → 调用时经 `tools/call` 转发执行。**即把 K3 的 FC 协议"跨进程/跨网络"延伸到任意外部系统。**
- **图**：Agent ↔ MCP client ↔ MCP server（远端工具）接入时序图。
- **伪代码**：`bridge_mcp_server(server)` → list tools → 包装成本地 Tool → `registry.register`。
- **与 K3 的关系（必讲）**：K3 的 FC 是"模型调工具的协议"；MCP 是"工具从哪来的传输层"。本地工具直接进 Registry，远端工具经 MCP 进 Registry——**入口不同，落点相同**，Agent 主循环无感。
- **陷阱**：把 MCP 当成"又一个工具框架"而忽视其"统一接入/解耦"价值；transport 选错（stdio vs 网络）；远端 schema 与本地校验脱节；忽略 MCP 的 auth/权限边界。
- **自检**：MCP 与直接调 API 的区别？为什么 MCP 能让"换工具源"不影响 Agent 代码？
- **引子→L9**：用 `tutorial/code/mcp_demo` 的 server，写 bridge 把它接入 `agent_core`，跑通"远端工具调用"。

### K10 能力模块 Skill（执行阶段 P5，前置 K9）
- **目标**：能定义 Skill（一组提示 + 工具 + 流程的封装）；能让 Agent 按需发现并加载 Skill；能区分 Skill 与 MCP（封装层 vs 传输协议）。
- **概念**：Skill、能力封装、发现/路由、按需加载（lazy loading）、Skill 与工具/提示/工作流的边界。
- **原理**：Skill = 把"某类任务怎么做"固化为可复用单元（含 system 提示片段 + 绑定工具 + 步骤模板）；Agent 遇到匹配任务时按名称/语义路由加载，注入上下文。**与 MCP 区别：MCP 解决"外部能力怎么连进来"，Skill 解决"连进来的能力怎么被组织、被发现、被按需调用"。**
- **图**：Skill 注册 / 发现 / 加载流程图（路由→取提示+工具+流程→注入 Agent）。
- **伪代码**：`load_skill(name)` → 取提示+工具+流程 → 注入 Agent 上下文。
- **陷阱**：把 Skill 和 MCP 混为一谈；Skill 过大变成"另一个 Agent"；Skill 提示与基础 system 冲突；Skill 无版本/无描述导致误加载。
- **自检**：Skill 与 MCP 的本质区别？何时用 Skill、何时直接加工具？
- **引子→L10**：用 `tutorial/code/skill_demo` 的真实 Skill，做"按需加载"的最小演示。

### K11 编排与框架（执行阶段 P6，前置 K7/K10）
- **目标**：用图/状态机编排多步；支持中断恢复与人工回环；能对照 LangChain/LangGraph。
- **概念**：graph、state machine、node、edge、checkpoint、human-in-the-loop、幂等。
- **原理**：声明式流程；状态持久化以便断点续跑；把 K3–K10 的模块串成流水线。
- **图**：工作流 DAG（节点=模块，边=流转，checkpoint 节点）。
- **陷阱**：把编排当万能胶忽略模块内逻辑；忽略幂等→重跑重复副作用；无 checkpoint 不可恢复。
- **自检**：图编排相比硬编 if/for 的好处？为何要 checkpoint？
- **引子→L11**：用图把 L3–L10 模块串成多步流程，支持中断恢复。

### K12 评估/可观测/安全（执行阶段 P6，前置 K11）
- **目标**：加轨迹追踪；做自动评分（含 LLM-as-judge）；设成本与越权护栏。
- **概念**：trace、eval、observability、guardrail、cost cap、hallucination、审计。
- **原理**：记录每步输入输出；多维度评分（正确/相关/成本/延迟）；护栏拦截越权。
- **图**：可观测面板（轨迹树 + 评分 + 成本）。
- **陷阱**：只评最终结果不评过程；忽视成本控制；护栏过严误杀合理请求。
- **自检**：为何过程级评估比结果级更重要？护栏如何兼顾安全与可用？
- **引子→L12**：给 Agent 加轨迹日志、自动评分与成本统计，产出可读报告。

## 4. 知识脉络（Knowledge Thread）

### 4.1 五核闭环 + 工具接入主线
主线以 K1 的 Agent Loop 为原点，逐章扩展能力：
```
K1 感知-思考-行动-观察（基础闭环）
 ├ K4 加记忆（长期/短期）
 ├ K3 加工具调用（FC，模型调工具的协议层）
 │   ├ K9 加 MCP（工具从哪来的传输层：做 server + 接入远端）
 │   └ K10 加 Skill（能力封装层：发现 + 按需加载）
 ├ K5 加推理与规划（ReAct + Plan）
 │   ├ K6 加反思（自修正）
 │   └ K7 加多智能体（角色协作）
 ├ K8 加知识（RAG）
 ├ K11 加编排（图/状态机，串起 K3–K10）
 └ K12 加护栏（评估/安全/成本）
```

## 5. 写作规范

- **术语表**：`glossary.md` 集中维护，章节只引用不重定义。
- **图**：mermaid 优先；类图用于模块、时序图用于交互、流程图用于机制。
- **伪代码**：Python 风格、可运行、带类型注解倾向；不依赖未引入的框架。
- **示例**：用真实片段（如一段 tool_calls 输出、一段 MCP `tools/list` 响应），避免"……"占位。
- **语气**：有观点、敢对比取舍；不堆砌名词。

## 6. 章节完成验收（Definition of Done）

一篇理论章视为完成，当且仅当：
- [ ] 七节齐全且达标（见第 2 节）；
- [ ] 学习目标可验证（能出题考核）；
- [ ] 至少 1 张图 + 至少 1 段原理级伪代码；
- [ ] 列明 ≥3 条常见陷阱并给"为什么错"；
- [ ] 自检题含 1 道开放设计/对比题；
- [ ] "动手引子"明确指向对应 Lab 与要验证的理论点；
- [ ] 含 2025–2026 前沿实务段（见第 2 节铁律）；
- [ ] 与对应 Lab 的能力目标逐条对齐（一致性检查表通过）。

## 4. 主流方案
