# K02 LLM 基础与提示工程（对应执行阶段 P1）

> 本章不只解释"提示工程是什么"，更给你一套**能立刻上手写提示**的方法：解剖模板 → 配方 → 坏/好对照范例 → 调试清单。学完进入 `项目教学区_Labs/L02_提示工程练习台/`：用 `PromptBuilder` 组装提示，并在 `challenge.py` 里亲手把一条糟糕提示改好、跑起来看模型行为差异。

## 一、学习目标
学完你能：
1. 说清 token / 上下文窗口的硬约束，以及 2025–2026 实务里"长上下文 ≠ 该全塞"的原因（lost-in-the-middle）；
2. 用**解剖模板**写出一条含角色 / 任务 / 约束 / 输出格式 / 示例的结构化提示；
3. 区分 JSON mode、native structured outputs、function calling 三档结构化手段，知道 Agent 为何主用 function calling；
4. 用一个**调试清单**修好答非所问的提示；
5. 在 L2 的 `challenge.py` 里把给定糟糕提示改成合规 JSON 输出。

## 二、核心概念（带前沿注记）
- **Token**：模型最小处理单位（英文≈1 词/token，中文≈1–2 字/token）。价格、延迟、上下文长度都按 token 计。**前沿实务**：把稳定的 system + few-shot 前缀用 **prompt caching**（Anthropic/OpenAI 均支持）缓存，可大幅降本提速——Agent 每轮都重发 system，缓存收益尤其大。
- **上下文窗口（Context Window）**：单次可见 token 上限，主流 128k–200k，Gemini 1.5/2 已达 1M–2M。**前沿实务**：窗口大了仍不能"全塞"——长文**中间信息易丢失**（lost-in-the-middle, Liu et al. 2023），且长上下文更贵。所以 K4 记忆压缩 / K8 检索（RAG）依旧必要。
- **系统提示（System Prompt）**：定角色、规则、输出格式的"稳定指令"，优先级最高，通常每轮开头注入一次。前沿做法：放**不变的行为约束**，配合 caching；用 delimiter（如 `#####`）把不可信用户输入与指令隔离，降低注入风险（K11 深入）。
- **用户提示（User Prompt）**：本次真实输入 / 目标（来自 K1 的 `goal`）。
- **Few-shot（少样本）**：在 system 之后、query 之前放 `(输入, 期望输出)` 示范，让模型"照葫芦画瓢"。**前沿实务**：不是越多越好——示例与任务分布不符会"污染"输出；更优是**检索式 few-shot**（按相似度从样例库挑，思想同 K8 RAG）；且示例顺序敏感，典型样本宜靠前。
- **结构化输出（Structured Output）**：要求模型输出贴合 schema 的结果。三档（见第六节）：JSON mode（仅保证格式合法）< native structured outputs（强制贴合 schema）< function calling（工具即结构化接口，本教学主线）。

## 三、工作原理
发给模型的 `messages` 是有序列表：

```
[system] → [user/assistant 交替的 few-shot] → [user 真实 query]
```

模型按此序列自回归生成下一段。Agent 的关键技巧：
- **用 system 锁死角色与输出格式**；
- **用 few-shot 给格式样板**（尤其结构化场景）；
- **用结构化约束把"自由文本"变成"可解析数据"**。

**前沿技巧·prefilling（assistant 前缀）**：在 assistant 首句预填 `{`，强制模型从 JSON 续写，几乎杜绝格式漂移；很多框架在底层这么做，理解即可，不必手写。

L2 的 `PromptBuilder` 就是把这套组装变成可复用代码，产出可直接喂给 `agent_core` 的 `LLMClient.complete(messages)`。

## 四、怎么写一条好提示（可复用方法）
这是本章核心：**写提示有模板和配方，不是凭感觉**。

### 4.1 解剖模板（六格）
```
[角色]   你是谁（边界、语气、专业度）
[上下文] 任务背景 / 可用信息 / 不可信输入隔离
[任务]   要做什么，输入是什么，输出是什么
[约束]   边界条件、禁止项、确定性要求
[输出格式] 固定模板 或 JSON schema（字段/类型/必填/枚举）
[示例]   1–3 个 (输入→输出) 样板，尤其给格式样板
```
缺哪一格都会出问题：无[角色]模型语气飘；无[输出格式]解析崩；无[示例]格式错。

### 4.2 配方（6 步）
1. **定角色与边界**：一句话锁死"你是谁、不做什么"。
2. **给上下文**：把完成任务必需的背景写清，用 delimiter 隔离用户原话。
3. **写清任务**：输入、输出、成功标准，越无歧义越好。
4. **规定输出格式**：结构化任务直接给 JSON schema（含 `required`、枚举、`description`）。
5. **放 few-shot**：挑与任务同分布的 1–3 个示例，典型样本靠前。
6. **跑一遍看失败再修**：用调试清单（第五节）迭代，别一次写完就交。

### 4.3 实战范例：口语 → 订餐 JSON
任务：把用户口语转成 `{intent: order|cancel|query, items:[{name,qty}]}`。

**糟糕提示（典型新手写法）**
```
你帮用户处理订单。
```
问题：无角色边界、无任务定义、无输出格式、无示例 → 模型自由发挥，输出不可解析。

**好提示（按模板写）**
```
你是订餐意图解析助手。
任务：把用户口语转成 JSON。字段 intent（枚举 order/cancel/query）、items（数组，每项 name 字符串 + qty 整数）。
约束：只输出 JSON，不要任何解释或多余文字。
示例：
用户：来两个汉堡
{"intent":"order","items":[{"name":"汉堡","qty":2}]}
```
逐行注解：
- `你是订餐意图解析助手` → 填[角色]，锁边界；
- `字段 intent（枚举…）items（…）` → 填[任务]+[输出格式]，枚举消除歧义；
- `只输出 JSON，不要解释` → 填[约束]，杜绝啰嗦；
- 示例 → 填[示例]，给格式样板，大幅降低格式错误。

同一句"我要取消三杯咖啡"：糟糕提示下模型回"好的，已记下"；好提示下回 `{"intent":"cancel","items":[]}`。**差异全在提示写法**——这正是 L2 `challenge.py` 要你亲手验证的。

### 4.4 输出 schema 设计小抄
- 用 `required` 标明必填，避免模型漏字段；
- 枚举（`enum`）比自由字符串稳，下游好处理；
- 字段 `description` 写清语义，模型更准；
- 禁 `$schema`/冗余嵌套，过严会让模型拒答（见陷阱⑤）；
- 数组项给明确结构，别用 `object` 空壳。

## 五、调试循环（答非所问时按此排查）
1. **指令模糊？** 任务/成功标准重写具体。
2. **缺输出格式？** 加 schema 或 prefilling。
3. **格式仍漂？** 加 few-shot 样板 + `只输出 JSON` 硬约束。
4. **few-shot 污染？** 示例与分布不符 → 换成同分布 / 检索式 few-shot。
5. **schema 过严拒答？** 放宽 `required` / 枚举，或允许 `null`。
6. **长文失效？** 信息在中间丢失 → 前置关键项 / 摘要 / RAG（K4/K8）。
7. **被注入？** 用户"忽略以上指令" → delimiter 隔离 + K11 防护。
提示也要**评测**：用固定样例集 + LLM-as-judge 打分（呼应 K11），而非肉眼看一条。

## 六、主流方案与前沿工具链
- **JSON mode**：模型只保证输出合法 JSON，不保证贴合你的 schema（最弱，仅适合简单场景）。
- **Native structured outputs / schema 强制**（OpenAI Structured Outputs 等）：严格贴合 schema、`additionalProperties=false`、枚举受控——结构化抽取首选。
- **Function calling**：把"工具"当成结构化接口，模型原生返回 `tool_calls`（K3 深入，本教学主线）。
- **Prompt caching**：缓存稳定前缀（system + few-shot），降本提速，Agent 每轮重发 system 受益大。
- **检索式 / 动态 few-shot**：按任务相似度从样例库挑示例，思想同 RAG（K8）。
- **LLM-as-judge**：用模型给提示输出打分，形成"写→评→改"闭环（K11）。
- **分隔符 + 特权指令标记**：隔离不可信输入、标记系统指令，注入防护雏形（K11）。

## 七、常见陷阱
1. **忽视上下文窗口 / lost-in-the-middle**：长文中间信息易丢，别全塞；用摘要/RAG。
2. **系统提示被注入覆盖**：用户"忽略以上指令"可能越权；delimiter 隔离 + K11 防护。
3. **Few-shot 与分布不符**：示例格式错 → 模型学歪；用同分布/检索式。
4. **不要求结构化输出**：自由发挥 → 代码解析崩（L1 必须坚持 JSON 决策）。
5. **schema 过严导致拒答**：`required`/枚举太窄 → 模型拒答；允许必要 `null`。
6. **prompt 里算数 / 查实时**：模型不擅长，交工具（K3）。
7. **稳定内容不缓存**：长 system 反复发 → 烧钱；用 prompt caching。
